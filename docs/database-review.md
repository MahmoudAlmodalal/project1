# مراجعة تصميم قاعدة بيانات BorrowHub MVP

## النتيجة وحدود الجاهزية

راجع التصميم مقابل [PRD](PRD.md) باعتباره المصدر الأساسي، مع الوثائق المشار إليها في [ERD](ERD.md). يغطي التصميم المسار المؤكد بخمسة جداول وخمس علاقات FK. هو قابل للمراجعة والرسم، لكن **اعتماد التنفيذ الكامل ينتظر قرارات الأعمال** بشأن الاستحقاق والتأخر والإجمالي والتعليق واستعادة كلمة المرور. لا توجد migrations أو شيفرة تطبيق ضمن التسليم.

## التغطية والقرارات

| موضوع المراجعة | النتيجة |
|---|---|
| الحسابات | FR-001–005 مغطاة: الاسم، البريد، الرقم الجامعي، القسم، الهاتف، hash، الدور والحالة. القسم أعيد من FR-001 رغم غيابه في §16 |
| المعدات والفئات | FR-006–010 و§14 مغطاة بكتالوج وفئة وأرشفة وأرصدة؛ reserved_quantity موجود رغم اختصارات FR-007 |
| دورة الطلب | FR-011–022: وحدة واحدة، الغرض، الفترة، سبب الرفض، التوقيت، الإرجاع والتلف؛ CANCELLED وEXPIRED مستمدتان من FR-016/018 وAC-07/08 |
| المتأخرون | FR-023–025: موعد تشغيلي وربط ببيانات الطالب؛ لا تخزن أيام التأخير ولا تضاف غرامة/حظر |
| التدقيق | NFR-008: ربط كل موافقة وتسليم وإرجاع/تلف بمسؤول؛ لا يعتمد على approved_by وحده |
| FK والتعددية | خمس FKs إلزامية إلى PKs من نوع uuid؛ كل تابع له أصل واحد والأصل له 0..N؛ لا FK إلى رقم جامعي نصي |
| التكرار والتطبيع | 3NF للوصف والعلاقات؛ الأرصدة والتوقيت الحالي مقابل الأحداث استثناءان مقصودان مضبوطان بالمعاملة |
| القيود | PK/UNIQUE/NOT NULL/CHECK ممثلة فعليًا في DBML؛ القيود العابرة للصفوف موثقة ولا يُدّعى أن CHECK يضبطها |
| حذف البيانات | RESTRICT يحمي تاريخ الإعارة والتدقيق؛ سياسة الاحتفاظ وتغيير الأدوار لم تُحدد |
| الجداول غير الضرورية | لا أصل مسلسل، تفاصيل طلب متعددة، إرجاعات مستقلة، جدول overdue، RBAC متعدد الأدوار، أقسام مُدارة، رسوم أو صيانة |

اختيارات **تقنية مقترحة وليست قواعد أعمال إضافية**: PostgreSQL، أسماء الجمع snake_case، UUID، timestamptz، text، فئة واحدة لكل صنف، مخزون داخل المعدات، requested_return_date مقابل expected_return_at، RETURNED مع is_damaged، أحداث تدقيق مستقلة، RESTRICT، الفهارس، وترتيب تواريخ المراحل. لا اسم فئة فريد ولا رقم هاتف فريد ولا سبب إلزامي لرفض الحساب.

## الفجوات وتعارضات المتطلبات

| الأولوية / المرجع | التعارض أو النقص | أثره والقرار الذي لم يُفرض |
|---|---|---|
| مانع تنفيذ — Q02/Q10 | FR-012 وDEC-02 من تاريخ البدء؛ AC-03 و§13 من التسليم؛ date مقابل timestamp | يحفظ الاختيار المطلوب والموعد التشغيلي؛ لا معادلة لإعادة الحساب ولا منطقة وقت مفترضة. يلزم تحديد العد الشامل وصفر أيام والاستلام المبكر والاعتماد المتأخر |
| مانع تنفيذ — Q03 | §16 وAC-06 تعرض OVERDUE؛ FR-021 يشترط CHECKED_OUT؛ DEC-01 لا يذكر OVERDUE | enum يدعم المصطلح دون فرض تخزينه؛ لا يمكن اعتماد عد النشط أو مسار إرجاع المتأخر قبل الحسم. الاقتراح الأبسط وسم مشتق فوق CHECKED_OUT، لكنه يحتاج اعتمادًا |
| مانع تنفيذ — Q04 | EC-02/US-08 تخصم total؛ AC-05/FR-010 لا تحدد ذلك | لا CHECK من نوع total=sum، ولا افتراض أن total يشمل أو يستبعد التالف. يجب تحديد معنى الإجمالي وعملية التلف والتعديلات الإدارية المتسقة |
| قرار مطلوب — Q05 | DAMAGED في F-04 مقابل RETURNED في AC-05؛ ملاحظات اختيارية في FR-022 | اقتراح RETURNED + is_damaged، والملاحظات NULL مسموحة وفق FR-022؛ لا تفرض تكلفة تلف أو إحالة صيانة وردتا في بعض المسارات التفصيلية |
| فجوة — Q06/SEC-02 | استعادة كلمة المرور مذكورة في §14 دون آلية؛ انتهاء الجلسة دون مدة/تخزين | لا اختراع reset_tokens أو sessions؛ يعتمد تصميم تخزينهما على آلية المصادقة المختارة. الوظائف غير مغطاة تفصيليًا ويجب حسمها قبل اكتمال التنفيذ |
| فجوة — Q07/Q12 | Suspend في §14 دون حالة في §16؛ إنشاء ADMIN غير موثق | لا إضافة SUSPENDED أو جدول عقوبات أو بيانات seed؛ يلزم تحديد الحالة والآثار والتزويد الآمن للمسؤول |
| قرار مطلوب — Q08 | أرشفة وتعديل أرصدة وحذف فئات بلا قواعد مرتبطة | RESTRICT حماية تقنية مؤقتة؛ لا تحرير حجوزات تلقائي أو خفض borrowed مباشرة أو حذف تاريخ عند الأرشفة |
| قرار مطلوب — Q09–Q11 | إلغاء APPROVED إداريًا وتمديد الإعارة غير مؤكدين؛ فشل الاعتماد قد يوصف رفضًا/انتظارًا | لا انتقال إداري إضافي؛ فشل تخصيص المخزون لا يسجل REJECTED دون قرار وسبب. سلوك الطلب بعد الفشل يحتاج تثبيتًا |
| قرار مطلوب — Q13/Q14 | إحصاءات الفصل بلا حدود فصل؛ عنوان damage/loss بلا مسار فقد | لا جدول semesters أو lost_status؛ يلزم تعريف النطاق قبل التقارير الدقيقة ومعالجة الفقد |
| قرار مطلوب — SEC-03/§15 | حماية بيانات الطالب وصلاحيات القسم دون هيكل متعدد الأقسام/المستودعات | لا اختراع warehouse_id أو عضويات موظفين؛ إذا كان العزل بين الأقسام مطلوبًا فهو نقص مؤثر في الهيكل |
| قرار مطلوب — §16/FR-001 | تفرد البريد لا يحدد case normalization، ونطاق الجامعة غير محدد | UNIQUE حاليًا على النص المخزن؛ تأكيد سياسة البريد ثم تطبيق canonicalization/فهرس مناسب قبل الإنتاج. الهاتف والرقم الجامعي يحفظان كنص |
| قرار مطلوب — الاحتفاظ | لا مدة احتفاظ ولا حذف/إخفاء هوية أو صلاحية تصدير سجل | الحذف المرجعي مقيد، ولا تستنتج سياسة تنظيمية من ذلك |

وصف دخول الحساب المعلق وعرض المعدات الصفرية Q01 لا يستلزم جدولًا جديدًا، لكنه يؤثر في الصلاحيات. الطلب المستقبلي يحجز فور الموافقة وفق FR-008/AC-02؛ ليس سؤالًا مفتوحًا هنا. التسجيل المكرر بالرقم الجامعي يمنعه UNIQUE وفق EC-03.

## الاتساق والتزامن

القيود الصفية لا تمنع عمليتين من استهلاك آخر وحدة أو إنشاء طلب ثالث. البروتوكول التقني المقترح:

1. **التقديم:** قفل صف users للطالب، إعادة فحص STUDENT/ACTIVE وعد الحالات النشطة، والتحقق من رصيد الصنف، ثم إدراج PENDING_REVIEW. جميع مسارات التقديم تلتزم القفل نفسه؛ لا حجز عند التقديم. حد التأخر يعتمد على Q03.
2. **تغيير حالة الطلب:** عند الحاجة لقفل الطالب اتبع ترتيبًا موحدًا: الطالب ثم الطلب ثم المعدات. يمنع ترتيب الأقفال المتباين deadlocks قدر الإمكان؛ يعاد تنفيذ المعاملة عند deadlock/serialization failure. لا تستخدم قراءة عرض قديمة لاتخاذ قرار تخصيص.
3. **الموافقة:** إعادة فحص PENDING_REVIEW، ثم تحديث أرصدة الصنف بشرط available_quantity>0، وتسجيل APPROVED وapproved_at وحدث المسؤول في معاملة واحدة. لا يكفي read ثم write بلا قفل أو شرط. عند فشل أي جزء rollback للجميع.
4. **التسليم مقابل الانتهاء:** كلاهما يقفل الطلب ويشترط APPROVED؛ الفائز فقط يحول reserved إلى borrowed أو available. يعاد فحص المهلة داخل المعاملة وفق قاعدة الوقت المعتمدة؛ لا مؤقت يبدأ من approved_at.
5. **الإرجاع المكرر:** يشترط وجود إعارة مستلمة غير مغلقة، ثم borrowed−1 وavailable+1 أو damaged+1، مع RETURNED والتوقيت والعلامة وحدث/حدثي التدقيق. إعادة الطلب بعد نجاحه لا تعيد الرصيد ولا تنشئ أحداثًا ثانية. القراءة اللاحقة تحدد النتيجة إذا فقد العميل الاستجابة.
6. **الأرشفة وتعديل المخزون:** يستخدمان قفل صف المعدات نفسه؛ لا يكتفى بفحص أعداد غير سالبة. يجب منع كسر تطابق الأرصدة مع الإعارات القائمة بعد اعتماد سياسة التعديل. لا CHECK إجمالي متعارض مع المصدر.

مطابقة reserved_quantity مع عدد APPROVED، وborrowed_quantity مع الإعارات المسلمة غير المعادة، تتطلب تدقيق اتساق ومعاملات موحدة؛ إن خُزن OVERDUE يدخل عد المستعار وفق تعريف الأعمال المعتمد. damaged_quantity قد يشمل رصيدًا ابتدائيًا/تعديلات إدارية، فلا يفترض مساواته بكل الإرجاعات التالفة التاريخية. قفل الصفوف والتحقق بالدور وآثار تغيير دور الحساب لا يمثلها FK وحده. الأحداث المطلوبة والتوقيت المطابق يجب أن تكتب مع الحالة؛ DBML لا ينشئ تلقائيًا triggers أو صلاحيات append-only.

## التحقق من الملفات

مصدر الهيكل [database.dbml](database.dbml)، ومخطط Mermaid مضمن في [ERD.md](ERD.md). روجعت صياغة الاثنين مقابل [DBML الرسمي](https://dbml.dbdiagram.io/docs/) و[Mermaid ERD الرسمي](https://mermaid.js.org/syntax/entityRelationshipDiagram.html).

نتائج التحقق الآلي في 2026-10-13، باستخدام أدوات مؤقتة خارج المشروع:

- نجح تحليل DBML باستخدام `@dbml/core` والمحلل الحالي `dbmlv2` الداعم لـCHECK؛ المحلل القديم `dbml` لا يدعم هذه الصياغة الحديثة.
- نجح تحليل مخطط `erDiagram` بواسطة `mermaid.parse` في Mermaid 10 ضمن JSDOM، بعد استخدام نسخة المتصفح المستقلة بسبب انتهاء مهلة تثبيت الحزمة. هذا فحص صياغة، وليس فحصًا بصريًا في mermaid.live.
- نجحت مطابقة الجداول الخمسة وجميع أسماء الأعمدة وأنواعها وعلامات PK/UK بين المصدرين، ومطابقة FKs الخمس وعلاماتها وتعدديتها وإلزاميتها.
- لم تضف تبعيات أو ملفات تحقق إلى المشروع. فحص `git diff --check` نجح؛ الملفات الجديدة روجعت مباشرة، لأن الملفات غير المتتبعة لا يشملها هذا الأمر.

صحة الصياغة لا تثبت سياسة أعمال، ولا تعني تطبيق القيود على قاعدة تشغيلية. لم تنشأ قاعدة بيانات أو migrations، ولم تختبر معاملات حقيقية أو أداء الإنتاج أو صلاحيات النظام. نطاق التغيير محصور في ملفات التوثيق الثلاثة؛ وثائق المتطلبات والرسوم السابقة محفوظة كما هي.
